## Goal

Every finding is fixed, from the twelve under "Fix first" to the cosmetic ones:
- A Merge restore only adds what's missing and never rewinds a newer record.
- A Replace restore on the sharing Mac updates the class in place, so the Assistant's phone never empties.
- Restored project sessions are back on their projects, and old broken ones are repaired.
- Edits to a to-do from Tide go to Tide; ticks are never lost by clearing.
- A failing sync says so once, not once per failed event.
- The Assistant recovers from a dead sync by itself and says what's happening; a fresh join never shows "Not in This Class," and Leave there can't purge the new class.
- Backups are written safely by hand too, failures and skipped files are shown, and half-downloaded notebooks never push out good backups.
- Every Remove Last Year and sharing-setup trap is closed.

Everything ends on main, built and tested on both apps (notebook on iOS and Mac, the Daybook Assistant on iOS), with a cold review of the combined work. No Core Data model change is planned, so no CloudKit schema deploy. Device checks become Tide rows.

## Decisions

Danny's choices (asked 2026-11-02):
- **Merge restore: newer wins.** A Merge skips a backup row whose stored record has a later `modifiedAt`. Nil on either side means the backup's row is taken. The preview counts those as kept, and the Settings line stays "Add what's in the backup and keep everything else", which is now true. (#1)
- **Tide edits: carried to Tide.** A notebook edit to the title or due date of a to-do that came from Tide goes across with `update_action` (`text` and `due`), the way a Tide reword already comes here. Tide refuses a due date newly set in the past: such an edit keeps the date here and is reported like the other "couldn't go across" lines. The editor's linked-note line changes to say edits go to Tide. (#3)
- **"View only" dropped** from the Mac's Add Member picker. The Assistant also reads its participant permission once after joining, and when it is read-only shows one plain line ("Your guide added you to view only. Ask them to let you make changes.") and keeps marking off. (#29)
- **Automatic-backup settings stay each device's own.** The four switches leave `BackupPreferencesService.preferenceKeys`; an old backup that carries them is ignored for them. (#19)

Settled here, without asking:
- **All 59 are fixed,** the cosmetic ones too: they are small and in files the agents open anyway.
- **Replace keeps the class's iCloud identity.** For the 15 share types, Replace updates records by `id` in place and deletes only the ids the backup lacks, as it already does for the names people set. This is right whatever the answer to the open Apple question on emptied zones (see Apple guidance). (#2)
- **The project-session repair lives with the launch repairs** (agent C), the importer's relink with restore (agent A), so no two agents edit one file.
- **The first-download lift asks twice** (#26), and the one-time repairs check the gate is armed rather than merely pending (#58); the auto-backup hold drops its 24-hour limit but writes `Partial-` files that trimming and "newest backup" skip (#14).
- **Notebook joins:** an unshared notebook that holds students refuses to join another guide's class (#8). A notebook legitimately joined as an assistant attaches its marks explicitly, as the Assistant does (#33).
- **The Assistant's stall rebuild** happens at most once per launch unless a send succeeded since, never while a sheet is up, and keeps the old screen until the new stack is ready (#42).
- **The Sharing Model text** in `Cosmic Daybook/CLAUDE.md` is corrected to 15 types, schema 22 (#34), in Phase 2's docs step.

Ruled out:
- **A new `modifiedAt` on `CDTodoItem`** to decide Tide edits by time: a schema change for a case "carry to Tide" settles without one.
- **Refusing Replace with sync on:** Replace is how a broken notebook is put right; it should be safe, not forbidden.
- **One agent per finding:** 59 agents would collide on files. Seven agents by file ownership keep every merge clean, which worked on 2026-10-05 and in Tide Phase 188.

## Apple guidance

Checked 2026-11-02 against the installed Xcode 27.2 (27B52) with the iOS, macOS and watchOS 27.2 SDKs; Apple's release-note index lists no newer release or beta. Documentation pages are dated 2026-10-08 unless said. Two facts that change the briefs: **the Daybook Assistant's deployment target is iOS 18.0** (`project.pbxproj`; `CLAUDE.md` says the phones run 26 and 27), so anything from iOS 26 or 27 needs `#available` there; and **Xcode is 27.2**, not the 27.1 `CLAUDE.md` names (Phase 2's docs step corrects both).

- **Emptying a share's zone (#2, agent A).** Apple says nothing definite about what happens to a CKShare or its zone when its last object is deleted: not `share(_:to:completion:)`, not the [CKShare page](https://developer.apple.com/documentation/cloudkit/ckshare), not the [sharing sample](https://developer.apple.com/documentation/coredata/sharing-core-data-objects-between-icloud-users), not WWDC21 10015. Only the owner deleting the share ends it; `purgeObjectsAndRecordsInZone` is the documented way to delete a zone. A forum thread (not Apple, unopened) says plain deletes leave empty zones behind. So the in-place update is the right fix, and A's test must not assume either outcome for an emptied zone.
- **Participant permission (#29, agent E).** `CKShare.currentUserParticipant?.permission` exists (`unknown`, `none`, `readOnly`, `readWrite`; iOS 10). Apple's recommended check for Core Data is [`canUpdateRecord(forManagedObjectWith:)`](https://developer.apple.com/documentation/coredata/nspersistentcloudkitcontainer/canupdaterecord(formanagedobjectwith:)) (iOS 14), with `canDeleteRecord…` and `canModifyManagedObjects(in:)`; it consults the participant's permission in the shared store. The error a read-only participant's save gets is undocumented (`CKError.permissionFailure` is documented only for the public database and share acceptance). E's read-only line should come from `canModifyManagedObjects(in: sharedStore)`, checked once after joining and after each share refresh, not from guessing the error.
- **Merge policy and authors (#53, agents E and G).** `NSManagedObjectContext.h` says `mergePolicy` defaults to `NSErrorMergePolicy`; a runtime probe on 27.2 confirmed `newBackgroundContext()` returns that with a nil `transactionAuthor`. Apple's [`transactionAuthor`](https://developer.apple.com/documentation/coredata/nsmanagedobjectcontext/transactionauthor) page says to set it before saving; [Consuming relevant store changes](https://developer.apple.com/documentation/coredata/consuming-relevant-store-changes) says to name contexts, keep a token on disk per store and fetch history on a background context, which the app does. Fix: take the context from `CoreDataStack.newBackgroundContext()`.
- **Dead mirroring delegate (#5, agent E; #4, agent C).** `NSPersistentCloudKitContainer.Event` exposes only identifier, store, type, dates, `succeeded` and `error`; no header defines 134421 or 134406. [Syncing a Core Data store with CloudKit](https://developer.apple.com/documentation/coredata/syncing-a-core-data-store-with-cloudkit) calls most errors transient and never says to recreate the container (the app's rebuild is its own choice, kept). New in iOS 27: `NSPersistentCloudKitContainer.EventChangedMessage` as an `AsyncMessage` (`.eventChanged`), SDK-confirmed; the notebook already uses it, the Assistant must guard it with `#available(iOS 27, *)` or keep the notification.
- **Dates with fractions (#20, agent B).** `JSONEncoder.DateEncodingStrategy` is unchanged in the 27.2 SDK; `.iso8601` writes whole seconds (probe: `08:00:00Z` for `.123`). `.custom` with `Date.ISO8601FormatStyle(includingFractionalSeconds: true)` writes milliseconds (`.122Z` for `.123`, so still truncated, but to the millisecond). Decode with `Date(s, strategy: Date.ISO8601FormatStyle(includingFractionalSeconds: true))`; the built-in `.iso8601` decoder accepts the fractional string but was not confirmed to keep the fraction, so the reader must switch too. Older archives have no fraction and must still decode.
- **Copying into iCloud Drive and listing placeholders (#9, #18, agent B).** `NSFileCoordinator`'s `.forReplacing` is for an item that replaces whatever is in its way, which covers write-elsewhere-then-rename. [`replaceItemAt`](https://developer.apple.com/documentation/foundation/filemanager/replaceitemat(_:withitemat:backupitemname:options:)) needs the source on the same volume (use `.itemReplacementDirectory`). A granted coordinated write starts a background task on its own. Apple's current docs never mention `.icloud` placeholder files; the documented way is `NSMetadataQuery` with the ubiquitous scopes, `URLResourceKey.ubiquitousItemDownloadingStatusKey` (`notDownloaded`, `downloaded`, `current`) and `startDownloadingUbiquitousItem(at:)`. B should go through the app's existing `UbiquitousFile` helpers for #18 rather than naming `.icloud` files, and read the status key.
- **Finishing an export in the background (#25, agent C).** [`beginBackgroundTask`](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(expirationhandler:)): call it before the work starts and pair it with `endBackgroundTask`; `backgroundTimeRemaining` is valid only once in the background. `BGContinuedProcessingTask` (iOS 26, not macOS) is for user-started work with visible progress; WWDC25 227 says not to use it for maintenance or backups. Nothing lets an app wait on Core Data's own export; the keep-alive stays a time-boxed task that watches events, as now.
- **iCloud Keychain conflicts (#15, agent B).** Apple's [Keychain syncing page](https://support.apple.com/guide/security/sec0a319b35f/web) (2024-05-07) says only that when two devices update the same item "one or the other is chosen." Which one is undocumented. `kSecAttrSynchronizable` and the access group are part of the primary key. So B's fix can't rely on a winner: stamp each key item with its creation date and keep every key for reading (`requireKey` tries each), and don't mint one while the first download is pending.
- **Core Data in iOS 26 (agent E's `#available` guard list):** the iOS 26 release notes changed Core Data's Sendable and MainActor annotations and removed the `NSPersistentStoreUbiquitous*` option keys; the iOS 27 notes fix saving a CKShare after an admin demotes themselves. Neither changes a fix here.

Where the plan goes against this on purpose: the Assistant keeps rebuilding its stack after a dead delegate (Apple never recommends it, and never offers an alternative that works; the rebuild is what brings marks back on her phone).

## Open questions
- Whether NSPersistentCloudKitContainer drops a share whose zone is emptied (#2): the Apple check answers it if Apple's documentation does. The fix chosen doesn't depend on it.
