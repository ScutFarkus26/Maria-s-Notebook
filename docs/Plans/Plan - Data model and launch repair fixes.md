## Decisions
**Danny's (2026-10-05):**
- **Fix all 64**, including the two rebuilds: the cross-process file lock (#17) and opening the store off the main thread (#19).
- **Old Siri marks outside the share:** once Siri is fixed, add this school year's unshared attendance to the share once, from the Mac (Settings › Classroom, with a count first), through the existing attach path. Never moves anything already in a share.

**Decided here:**
- **No schema change, no CloudKit deploy.** Delete rules stay as they are (#6 detaches notes in code instead of changing `WorkCheckIn.notes` to Nullify). If a phase believes it needs a model change, it stops and reports.
- **Duplicate keepers by identity, winners by content (#1, #40).** The row kept is chosen by something that is the same on every device at every sync state: the `id` string first (attendance and per-child copies have different ids), then the CloudKit record name only to break an `id` tie, then object URI. Not record name first: a copy not yet sent to iCloud has none on its own device, so two devices could each keep the other's copy (reviewer, 2026-10-05). The winning content (the comparator's winner: marked > automatic absence > latest `modifiedAt` …) is copied onto the kept row, `modifiedAt` included, **only when the winner's `modifiedAt` is newer than the kept row's**, so a device with a stale view never lowers it. The read-side `AttendanceDeduplication.wins` stays the content rule. Generic same-id groups keep today's order (createdAt, record name, URI).
- **Never delete what may still be downloading (#7, #22).** Orphaned check-ins get the same "missing on passes at least a day apart" ledger as students, generalized from `OrphanStudentGrace` (a second key, not a second mechanism), and nothing is deleted while `FirstDownloadGate.isPending()`. The grace also requires a successful import, into the store that holds the missing kind of row (on the guide's devices students and work are both in `private.sqlite`), after the first sighting (#22). Import dates aren't recorded today: 1D records the last successful import end per store (G4) behind a small reader in a new file; 1B's grace takes it as an injected closure (with none, no import is known since the first sighting, so the id keeps waiting); Phase 2 wires the real reader.
- **Retired outcome (#8):** `completionOutcomeRaw` is cleared when the launch merge folds it (1B) and in `CDWorkModel.status`'s setter (1C, `WorkModelEntity.swift:97`), which every status write goes through; 1B also covers any writer that sets `statusRaw` directly (MCP, undo snapshots). Dedup stops copying it (1C). The old comment "it is the record of what was there" goes: the folded status is that record.
- **Check-in deletes keep the work's notes (#6):** before a check-in is deleted, notes that also belong to its work (`note.work != nil`) are detached (`workCheckIn = nil`); the check-in's own notes still go with it. Done in one place (`CDWorkCheckIn.prepareForDeletion`), so every delete path is covered.
- **Clean Up Old Records (#4):** completion entries that carry notes keep the notes (detached, still in student notes); the preview says how many notes are kept.
- **Error screen (#9):** "Re-download from iCloud…" is hidden for "opened by a newer version" and refused with a plain message when iCloud sync is off; otherwise it arms the existing deferred `resetLocalCacheOnLaunch` and quits, never deleting files in-process (the reset itself uses `destroyPersistentStore`, G6). 1A hides "Restore Backup" for "newer version" and leaves the rest of it to Phase 3, which designs it: the importer needs a loaded store's context, a fresh store would trip #32's first-download refusal, and iCloud downloading into a restored store would duplicate everything. Phase 3's constraints: never delete the failed store (move it aside, keep it); never let a restore and an iCloud download fill the same store; reuse "restore into a fresh notebook" (5ccfa2f2) where it fits; if it can't be made safe, the button becomes plain guidance ("Re-download from iCloud, then restore from Settings › Data") rather than a dead button.
- **Fallback chain (#13):** when `private.sqlite` exists and fails to load, the app goes to the error screen; the separate local unified store is only for a device with no split stores at all.
- **Tests never open the live store (#15):** `getSharedCoreDataStack` returns an in-memory stack under XCTest. Until 1A lands, no phase runs macOS tests (iOS simulator only).
- **One lock for store surgery (#17):** a sidecar lock file next to the stores. Every process holds a *shared* `flock` for its life; surgery (the reset, migration backup and restore, stale-key repair, orphan-metadata cleanup, schema stamp) takes an *exclusive* non-blocking lock. When a migration or an armed reset is due and the exclusive lock isn't free, the store is not opened: the reset stays armed and the screen says, in plain words, to close the other copy of Cosmic Daybook. Routine surgery that isn't due just skips and logs. `resetLocalCacheOnLaunch` becomes environment-scoped. Only a process that could take the exclusive lock at launch (the primary) runs dedup and launch repairs (Phase 2 wires this into `MigrationRunner` and `DeduplicationCoordinator`).
- **Assistant store (#18):** under `ASSISTANT_APP`, an incoherent shared store throws `.storeSchemaIncoherent` to the Assistant's startup screen (its warned rebuild) instead of being moved aside.
- **Siri (#2):** the orphan guard starts when the shared stack is created for any caller (1A, in `getSharedCoreDataStack`; the window bootstrap's call stays and is idempotent), since a background intent brings up no scenes (G8); `SiriHost.didSave` enqueues and flushes as a backstop (1D). Every App Intent that writes a classroom record is checked (1D).
- **Share waiting list (#3, #21, #27):** filter to unshared, in-scope records before capping; no silent cap while a pin exists (log instead); always enqueue, even with sync off; entries carry a stamp so one re-added mid-flush survives. A returning student's attendance is queued only when the student herself is unshared.
- **Setup vs guard (#28):** one shared "attaching" flag: the guard's flush waits while Set Up Classroom Sharing or Add Them to the Share runs, and the first chunk is re-checked as unshared too. Setup keeps the waiting entries its attach failed on.
- **History (#29, #64):** export starts are kept per store and each purge is scoped to its store (`affectedStores`); future-dated starts are ignored. The transaction author gets a per-process suffix; only this process's author counts as own, so another running copy's saves are merged and announced (G5). The old bare `CosmicDaybook` author also counts as own, so the first launch of the new build doesn't react to all of its own history again. Only the primary process (see the lock) runs dedup and repairs in reaction.
- **Email settings (#25):** the shared settings row is written from the settings screen's edits (and once when the row is missing), never by the launch copy.
- **Scheduled-day mirror (#49):** the launch repair stops rewriting it (nothing fetches by `scheduledForDay`); writes at schedule time stay.
- **Backups (#10, #35, #36):** `absenceReasonRaw` round-trips raw; older formats keep attributes they predate (by `envelope.formatVersion`, optional attributes included); mirrored EventKit rows are skipped on restore and rebuilt by the next sync (no format bump). If 1E finds a format change unavoidable, it bumps to v39 and says so.
- **Restore gates (#32, #38):** restore is refused, in plain words, while `FirstDownloadGate.isPending()` or when the notebook's role isn't lead guide.
- **Store loading off the main thread (#19, Phase 3):** the stores load on a background task behind the existing "Opening your notebook…" state; callers that need the stack (App Intents, the MCP server, the Mac's app delegate) await one shared async accessor. No change to what loads, only where.

## Apple guidance
Checked 2026-10-05 against Xcode 27.0 (27A266a), iOS 27.0 / macOS 27.0 SDKs (the Assistant and three other targets deploy to iOS 18.0). Xcode 27.1 RC and 27.2 beta 2 exist; their release notes name nothing for Core Data, CloudKit or App Intents, so no Xcode update first. Core Data doc pages are dated 2026-08-14 and are mostly one-line abstracts; the SDK headers are the source where they disagree.
- **G1 `fetchShares(in:)`** is synchronous only and reads local mirroring metadata ("does not [do] any network work", `NSPersistentCloudKitContainer_Sharing.h`). Apple documents no blocking, but the project has seen it wait behind an import/export, so main-actor callers use the existing `@concurrent` `ClassroomShareAttach.shares(inStoreWithIdentifier:)` (#26). No reference page exists for the sharing methods (404).
- **G2 `share(_:to:)`** fails, or reassigns, when any object (or one its traversal reaches) is already shared (header; [WWDC21 10015](https://developer.apple.com/videos/play/wwdc2021/10015/)). Never call it on shared objects (#3, #28, the one-time step).
- **G3 `recordID(for:)`** returns nil, `recordIDs(for:)` `[:]` and `fetchShares` `[]` for a store with `cloudKitContainerOptions == nil` (probe on macOS 27.0, not documented). That confirms #20: with sync off, every copy looks unexported; skip destructive dedup there.
- **G4 First download:** no "initial import finished" API. Apple's only example waits for `.import` with the store's identifier and `endDate != nil` ([WWDC22 10119](https://developer.apple.com/videos/play/wwdc2022/10119/)). iOS 27 adds the typed `NSPersistentCloudKitContainer.EventChangedMessage` (`.eventChanged`, docs 2026-09-11), a wrapper only (#56, #22). It is iOS 27 only: not in Assistant-compiled code.
- **G5 History:** `deleteHistory(before:)` takes a date, token or transaction; `affectedStores` (from `NSPersistentStoreRequest`) scopes it to one store; how purging interacts with CloudKit's own history use is undocumented, so keep the export-date gate (#29). Transactions carry `processID`, `bundleID`, `author`, `contextName`; author is only what we set (#64). `NSPersistentStoreRemoteChange` is posted for writes by other processes too, with the post-option key set (#64).
- **G6 Copying, removing and destroying stores:** `remove(_:)` leaves files alone. `destroyPersistentStore(at:type:options:)` honors SQLite locks and journals and truncates rather than unlinking under another process. `replacePersistentStore(at:destinationOptions:withPersistentStoreFrom:sourceOptions:type:)` copies a store with its WAL safely (pass the same options as `addPersistentStore`). [QA1809](https://developer.apple.com/library/archive/qa/qa1809/_index.html) (2014): copying only the main file under WAL loses data. So the reset (#9) and the pre-migration backup and restore (#16, #17) use these coordinator APIs, not file copies or `removeItem`.
- **G7 Migration error codes** (`CoreDataErrors.h`, NSCocoaErrorDomain): 134020 incompatible schema, 134100 version hash, 134110 migration, 134111 constraint violation, 134120 cancelled, 134130 missing source model, 134140 missing mapping model, 134150/134160 manager source/destination store, 134170 entity migration policy, 134190 inferred mapping model, 134505/134506 staged migration. All of these mean "this build can't open these bytes" (#13).
- **G8 App Intents:** a background intent launches the app "in a special mode without scenes" ([WWDC22 10032](https://developer.apple.com/videos/play/wwdc2022/10032/)), so `WindowGroup` `.task` doesn't run (#2). Register shared dependencies early, in `App.init` (`AppDependencyManager.shared.add`, [WWDC25 244](https://developer.apple.com/videos/play/wwdc2025/244/)). `openAppWhenRun` is deprecated since 26.0 in favor of `supportedModes` (leave as is unless touched). iOS 27's `allowedExecutionTargets` can run an intent in an extension process, which would be a second writer to the store ([WWDC26 345](https://developer.apple.com/videos/play/wwdc2026/345/)). Keep intents in the main app (`.main`), and give the lock (#17) and author suffix (#64) per-process handling. Intents have a 30-second limit (Phase 3's async accessor must not wait longer).
- **G9 Delete rules** are not part of entity version hashes (headers, plus a probe with nullify, cascade and deny all hashing the same), and CloudKit stores relationships as `CD_<name>` fields. So a delete-rule change would need no migration and no deploy. This plan still makes none (Decisions).
- **G10 iOS 27 release notes:** apps built with the iOS 27 SDK must use the scene-based life cycle. The SwiftUI `App` already does, and Phase 3 must keep it.
