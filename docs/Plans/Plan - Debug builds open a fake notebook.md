# Debug notebook: Debug builds never open the real notebook

> **Not started.** Written 2026-10-04.
> In short: Debug builds open a fake, local-only notebook; the real one only through the Real Notebook scheme.
> From Danny's question "would a fake notebook for a debug build be a good idea?" (session branch `claude/fake-notebook-debug-builds-093156`).

## Goal
Every Debug build (Mac, simulators, Danny's iPhone and iPad, unit-test host) opens a separate, local-only **debug notebook** filled with a realistic fake class: about 22 children across Lower, Upper and Adolescent, the outline of Danny's real lesson list, and about six weeks of attendance, presentations, work, notes and meetings, moved forward to today each day. Debug builds do nothing to Danny's real data: no store, no iCloud sync, no iCloud key-value prefs, no backups, no Spotlight, no Reminders, no notifications, no MCP server. The real notebook opens only through a second Xcode scheme, **Cosmic Daybook (Real Notebook)**, which passes `-UseRealNotebook`. Release builds are unchanged. A Debug Daybook Assistant opens a fake class the same way.

## Decisions
- **Every Debug build opens the debug notebook by default (Danny).** The real one only with `-UseRealNotebook`, set by a second shared scheme. Release ignores the argument (compiled out). Ruled out: Mac-and-simulator only (Debug installs on devices would still open the real notebook); opt-in only (gives data, not safety).
- **One process-wide `NotebookProfile` (`.live` / `.debug`) resolved once at launch (decided here),** like `AppLaunchMode` (`Cosmic Daybook/AppCore/AppLaunchMode.swift`). `.debug` = `#if DEBUG` and no `-UseRealNotebook`. Under XCTest it is `.debug` too, so the test host stops opening the real store files (it does today: `AppBootstrapping+CloudKit.swift` fallback 2 opens the split stores and runs `prepareStoresForLoad`).
- **Store location (decided here):** `.debug` stores live in `<AppSupport>/<bundleID>/DebugNotebook/`. `CoreDataStack.storeDirectory()` (`AppCore/Persistence/CoreDataStack+Stores.swift:32`) returns it for `.debug`, so private/shared/unified URLs, Reset Local Cache and the first-download gate all move with one switch. CloudKit is forced off for `.debug` in `createCoreDataStack` (`AppBootstrapping+CloudKit.swift:35`), whatever `enableCloudKitSync` says; `localStoreURL` stays nil so the normal launch path (history processor, launch repairs) is exercised against the debug files. The CloudKit build environment (Production) is untouched.
- **UserDefaults (decided here, corrected in review):** a new `NotebookProfile.scoped(_:)` returns the key unchanged in `.live` and appends `.DebugNotebook` in `.debug`, so Release keeps every key name it has today. (Putting these keys on `CloudKitEnvironment.scoped` would rename them `.Production` in Release, since both configs build for Production, and Release would lose onboarding and its sync setting.) `CloudKitEnvironment.scoped` composes it, so already-scoped sync state also separates in `.debug`. Keys moved onto `NotebookProfile.scoped` (shared with Release on the Mac today): `resetLocalCacheOnLaunch`, `useInMemoryStoreOnce`, `enableCloudKitSync`, `cloudKitActive`, `lastStoreErrorDescription`, the schema-coherence keys (`+SchemaVersion.swift:236`), `hasCompletedOnboarding` (incl. the `@AppStorage` uses in `CosmicDaybookApp.swift:20` and `OnboardingView.swift:7`), the auto-backup keys, `SpotlightIndexer.lastIndexedFingerprint`, `ReminderSyncService.syncListIdentifier` and the calendar IDs. Plain UI preferences (sort orders, layout) stay shared; harmless.
- **iCloud key-value store (decided here):** for `.debug`, `SyncedPreferencesStore` (`Services/Sync/SyncedPreferencesStore.swift`) uses a local UserDefaults suite (`CosmicDaybook.DebugNotebook`) instead of `NSUbiquitousKeyValueStore`, and `SchoolYearSync.start()` doesn't run. Otherwise a Debug build writes front-desk addresses and the school-year start to every real device.
- **Gated off for `.debug` (decided here; the check goes inside each service, not at launch call sites, because several are also triggered later):** auto-backup (quit backup in `AutoBackupAppDelegate.swift:81`, scheduled loop `AutoBackupManager.swift:114`, iOS background/BGTask backups) — fake backups would push real ones out of the keep-10 retention; CloudKit share acceptance, invitation collection and `SharedStoreOrphanGuard`; ubiquity refresh and `PhotoStorageService.moveLocalPhotosToICloud`; the photo-orphan cleanup; Spotlight (`SpotlightIndexer`) and `updateAppShortcutParameters`; Reminders and Calendar sync (Reminders writes completions back to the real list); `FrontDeskEmailReminder.reschedule` and parent-report notifications (same notification center as Release on the Mac); push registration; the MCP server (port 43117; it serves the primary stack, and the bridge's `open -b` can wake a Debug copy). Each is one `NotebookProfile.current.allowsRealWorldEffects` check at the service's entry: `FrontDeskEmailReminder` (also called from `AttendanceEmail.swift:102` and `AttendanceExpandedView+FrontDesk.swift:94`), `ParentReportNotificationService`, `ReminderSyncService` and `CalendarSyncService` (also driven by `ReminderChangeListening` / `EventKitChangeObserver`), `SpotlightIndexer`, `MCPServerService`, `AutoBackupManager`; launch-only work (share inbox, push registration, `SharedStoreOrphanGuard`) is gated in `AppServicesLauncher` / `AppBootstrapper`. No scattered `#if DEBUG`.
- **Real iCloud containers (decided in review):** `CloudKitConfigurationService.container` asserts `.live` (direct `CKContainer` calls in `ClassroomSharingService+Setup.swift:23`, `+Members.swift:136`, `ClassroomShareRelease+Live.swift:214`, `ClassroomShareAttach.swift:230` bypass the stack's CloudKit switch), and in `.debug` Settings › Classroom sharing and release show "Sharing is off in the debug notebook." `UbiquityContainerCache` returns a local folder `DebugNotebook/iCloud/` in `.debug`, so photos, album PDFs and the album shelf never reach real iCloud Drive.
- **Backups redirected where they're written (decided in review):** `Backup/Core/BackupDestination.swift` (≈55) points every backup in `.debug` at `DebugNotebook/Backups/`, with its own retention. That covers the scheduled and quit backups, Export Backup, `ClassroomShareRelease.backUp`, MCP `create_backup` and `BackupFolderMigration`, which otherwise write to real iCloud `Documents/Backups` and push real backups out of the keep-10 retention.
- **Sample Class in Debug (decided in review):** `sampleClassroomStoreURL()` goes under `DebugNotebook/` in `.debug`; today it's in the base folder, so a Debug Sample Class would overwrite Release's.
- **CloudKit schema runs (decided in review):** `-InitializeCloudKitSchema` requires `.live` and fails loudly otherwise; the schema-run recipe in `Cosmic Daybook/CLAUDE.md` (≈219) and `docs/Technical notes/BUILD_SETTINGS.md` says to use the Real Notebook scheme. The "a Debug launch on the Mac opens the live notebook" warnings move to the Real Notebook scheme instead of being deleted.
- **Deletion guard (decided in review):** the daily rebuild and "Rebuild Debug Notebook" delete only paths built directly from `baseStoreDirectory()/DebugNotebook/` (never via `storeDirectory()`), and only when the profile is `.debug` and the last path component is `DebugNotebook`; `-FreshDebugNotebook` is ignored when `-UseRealNotebook` is also passed. Each guard has a test.
- **Visible label (decided here):** in `.debug` the window title ends " — Debug Notebook" (Mac) and the sidebar/tab chrome shows a small "Debug Notebook" capsule (`RootView+Chrome.swift`, next to where the Sample Class indicator goes). In `.live` Debug builds the capsule reads "Real Notebook" in orange, so a deliberate real-notebook run is never mistaken for a safe one.
- **Rebuilt each day (decided here):** the debug notebook stores the day it was seeded (`DebugNotebook.seededDay`, scoped); on the first launch of a new day the store files are deleted and reseeded, so dates line up with today and edits survive within the day (the Assistant's sample works the same way). `-FreshDebugNotebook` forces a rebuild (for agent simulator checks); a Debug menu item "Rebuild Debug Notebook" does it by hand. Not seeded under XCTest (tests make their own stacks; seeding would slow every run).
- **Lesson outline (Danny):** the repo is public, so only the outline is committed: title, area, sequence, order in sequence, sort index, section, key-lesson mark, prerequisites/related IDs, lesson format, age range. No write-ups, materials, teacher notes, purposes, attachments, file bookmarks or anything about children. File: `Cosmic Daybook/AppCore/DebugNotebook/LessonOutline.json`, excluded from Release (Release `EXCLUDED_SOURCE_FILE_NAMES`, the same mechanism as d86bc746). It's produced by a Debug-only menu command, **Troubleshooting (Debug) › Save Lesson Outline…**, enabled only with `-UseRealNotebook`; Danny runs it once (a Tide item). Until the file exists, the seeder uses ~40 made-up lessons built into the code, so nothing waits on him. Ruled out: full snapshot kept outside git (copy build step, missing in agents' worktrees); copying from the real store at launch (that's the thing Debug must not open).
- **Fake class (Danny: like the real class):** ~22 children (Lower ~9, Upper ~9, Adolescent ~4), fixed UUIDs, short names in the canonical "Maya S" form; six weeks of school days from `SchoolCalendarService` rules (class start rule: never assume Sep 1); attendance with a few absences, lates and one left-early; ~300 presentations following each child's sequence position; work through `WorkLogService` only (the single writer of `WorkStatus`), with check-ins; notes; a few meetings and follow-ups; a Restock shelf; guardians with `example.org` addresses; front-desk and office addresses `@example.org` in the debug synced-prefs suite. Built on `SampleClassroomSeeder`'s pieces (its fake-records code is reused, not duplicated); Sample Class itself keeps working in Debug and mirrors from the debug notebook.
- **Assistant (Danny: in this plan):** a Debug Assistant without `-UseRealNotebook` opens the existing daily on-disk sample class (`Daybook Assistant/AssistantSampleClass.swift`, the join screen's sample: 22 children, Day 37, Restock shelf) straight away, skipping join; Siri and keep-alive stay off as they already are for the sample. Its Debug scheme gets a "Daybook Assistant (Real Class)" twin. It reuses the Assistant's own sample rather than the notebook's fake class: the Assistant reads the class through the CKShare, which can't be faked locally. No share accept or attach may run in this mode.
- **Assistant during Phase 1 (decided in review):** the Assistant compiles `CoreDataStack+Stores.swift`, `CloudKitEnvironment.swift`, `UserDefaultsKeys.swift` and `FrontDeskEmailReminder.swift` by path. `NotebookProfile.swift` is added to the Assistant target too, and under `ASSISTANT_APP` the profile is always `.live` until Phase 3 changes that, so Phase 1 doesn't move the Assistant onto an empty store with CloudKit still on.
