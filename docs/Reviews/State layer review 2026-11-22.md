## One fact several items rest on

The `@Observable` macro in Xcode 27.2 generates a `shouldNotifyObservers` check (`Observation.swiftinterface:25`; the setter in the macro plugin is `guard shouldNotifyObservers(_x, newValue) else { _x = newValue; return }`, comparing Equatable values with `!=` and plain class references with `!==`), so setting a property to a value equal to the old one stores it but doesn't tell views. `withMutation(keyPath:)` has no such check, so it always notifies. Apple documents none of this. That makes the many hand-written `if x != new { x = new }` guards redundant (harmless), and it matters in two places: arrays of Core Data objects compare by identity, so re-assigning the same students after one was edited sends nothing (B4), and `AppRouter.NavigationDestination` has a custom `==` that ignores its payload (item 22). A small test compiled with this toolchain (`swiftc`, 2026-11-22) confirms it: re-assigning an array of the same `NSObject`s sent 0 notices, an equal `Int` 0, a changed `Int` 1, and a struct whose custom `==` ignores a field stored the new field but sent 0 notices.

### B1. A lesson opened in its own Mac window likely crashes — **checked** in code, not reproduced
`Lessons/Detail/LessonAlbumLinkSection.swift:12` declares `@Environment(AlbumLibrary.self) private var library` (not optional) and reads it in `body` (`:60`). It is drawn for every lesson from `LessonDetailView+InfoSections.swift:29`, and the lesson window (`LessonDetailWindowHost` → `EntityWindowHost` → `LessonDetailView`) is opened by three buttons (`LessonDetailView.swift:118`, `LessonAssignmentHistoryView+Rows.swift:171`, `LinkedNotebookLessonsPanel.swift:93`). The detail-window gate (`AppCore/Windows/DetailWindowScene.swift:166-172`) puts in the classroom, calendar, router, save and restore coordinators, and neither it nor `EntityWindowHost` puts in `AlbumLibrary`; only the main window (`CosmicDaybookApp+MainWindow.swift:67`) and the album window (`CosmicDaybookApp.swift:173`) do. A missing non-optional environment object is a fatal error. The section has been there since at least 2026-09-17 and no bug hunt mentions a crash, so whoever fixes it starts by reproducing it. **Fix:** `.environment(AlbumLibrary.shared)` in the gate, beside the restore coordinator. The same gap is in `AppCore/PreviewEnvironment.swift:23-35` (no `AlbumLibrary`, no `RestoreCoordinator`), so previews of those screens would crash too. S, safe.

**Landed** (Phase 3, 41365ce41): the detail-window gate now supplies `AlbumLibrary.shared`, and both preview environments supply it and a `RestoreCoordinator`. Not reproduced first (the plan's D2: that needs clicks in the Mac app); the Mac app builds in Debug and Release. Opening a lesson in its own window is still to be [checked on the Mac](tide://box/Areas/App%20Development/Cosmic%20Daybook/To%20do.md?text=State%20layer%20fixes%20Phase%203%3A%20on%20the%20next%20Mac%20build%2C%20open%20a%20lesson%20in%20its%20own%20window%2C%20change%20the%20viewing%20year%20in%20the%20Sample%20Class%2C%20and%20press%20Back%20Up%20Now).

### B2. Ready and Brewing can stay stale after two updates overlap — **checked**
`Presentations/Overview/PresentationsViewModel.swift:207-230` saves the "what I last saw" hashes and `lastUpdateDate`, then yields at `:258-259` and returns if cancelled, before it sets `readyLessons`/`blockedLessons`/`blockingResults` at `:273-275`. A second `update()` (the 200 ms debounce, the appear task, memory pressure) cancels the first during that yield, sees nothing changed (`:201`), and returns. The lists keep their old values, or stay empty on first load, until some input changes again. **Fix:** move the hash and date writes below the last cancellation check. S; only the cancelled path changes.

**Landed** (Phase 1, 38de6a77f): the six hashes, `lastUpdateDate`, `cachedLessonAssignments` and `cachedAssignmentsGeneration` are written after the last cancellation check, beside the three lists. `PresentationsOverlappingUpdatesTests` failed before and passes after. Corner left: the lookups written before the last pause can hold a cancelled update's inputs if those inputs change back before the next update.

### B3. Every Notes tab leaks its view model — **checked**
`Students/Notes/StudentNotesTimelineView.swift:12-21` stores a reload closure on the model as an Objective-C associated object, and `:45-47` sets it to `{ newViewModel.fetchAllNotes() }`. The closure holds the model and the model holds the closure, so the model, its student and its note rows are never freed. It also needs a `nonisolated(unsafe)` key. **Fix:** delete the extension, the setup and `reload()` (`:502`); call `viewModel.fetchAllNotes()` at `:106` and `:122`. S, safe: that closure was the only thing `reload()` ever did.

**Landed** (Phase 2, f02251add): the associated-object extension, the setup and `reload()` are gone; the two call sites call `viewModel.fetchAllNotes()`. No test can reach a view's setup, so the check is that the file holds no `objc_setAssociatedObject`, `objc_getAssociatedObject` or `nonisolated(unsafe)`.

### B4. The roster doesn't tell views when a student is edited — **checked** (the mechanism is tested; which screens show it isn't)
`Students/Roster/RosterStore.swift:55-67` rebuilds `all`, `enrolled` and `byID` from the fetched results controller. After a rename or level change they hold the same objects in the same order, so with the equal-value skip none of the three notifies, which contradicts the class comment ("invalidated through observation when the controller reports a change"). Views that show `student.fullName` or group by `student.level` from `roster.all` without observing the row object could stay stale until something else redraws them. `shortNamesByFullName` still notifies on a rename (it holds strings). **Fix:** wrap the three assignments in `withMutation(keyPath:)`, which has no equality check, so they always notify, as designed. Needs care: those views redraw a little more, which is the original intent. Confirm with a test that renames a student and watches `roster.all`.

**Landed** (Phase 2, f02251add): `refresh()` writes `_all`, `_enrolled` and `_byID` inside `withMutation(keyPath:)`, so each notifies once on every change the controller reports. `RosterStoreEditNotifiesTests` (a rename on `all`, a level change on `enrolled`) failed before and passes after.
