> **Not started.** Found at main 0bd5c3225 (2026-11-22); nothing fixed yet.
> In short: the view models are already built the modern way (Observation, main-actor by default, no `ObservableObject`), so the gains are in three places: a few real bugs, state that's tracked or kept alive when nothing needs it, and expensive work done every time a screen redraws.

**Scope.** "State" here means the view models (67 `*ViewModel*` files), the two controllers (`IdleMemoryTrimController`, `MCPIdleQuitController`), the screen models and stores views own (`MeetingQueueModel`, `MeetingDraftModel`, `ClassGrid*Model`, `SchedulesPageModel`, `PresentationSession`, `RosterStore`, `SchoolYearStore`, `ClassroomWorkspaceStore`, `AppRouter` and the window request objects), and how views create and hold them. Left out, and not read by anyone: services, backup and sharing internals; the Daybook Assistant's own state classes; the album state (`AlbumLibrary`, `AlbumIntelligence`, the semantic index, the PDF viewer); `LessonCatalog`; ParentLocker sign-in and sync; the Toast, Speech and command-bar services. None of the classes the items below touch is compiled into the Assistant, so its iOS 18 floor doesn't apply to them. Four read-only reviewers each took an area; the items marked **checked** were then read by hand at the cited lines. Nothing was built or run except one small Observation test (below). Paths are under `Cosmic Daybook/`.

**Already right, so left out:** no `ObservableObject`, `@Published`, `@StateObject` or `@EnvironmentObject` anywhere (the 14 `@ObservedObject` are all on Core Data objects, which is correct); no `.onAppear { Task { … } }`; most heavy screens already create their model after appearing (`TodayRootView`, `PresentationDetailView`, `SchedulesView`, `DataManagementGrid` and others); `State(initialValue:)` sites are all protected by `.id(…)` or one-window-per-value; `MeetingQueueModel`, `MeetingDraftModel`, `CurriculumMapStore`, `ClassGridYearsModel`, `ChecklistHover` and `AttendanceViewModel` are textbook. Not findings by project rule: a missing `@MainActor` (the default is main-actor), `@Query`, `DispatchQueue`.

## One fact several items rest on

The `@Observable` macro in Xcode 27.2 generates a `shouldNotifyObservers` check (`Observation.swiftinterface:25`; the setter in the macro plugin is `guard shouldNotifyObservers(_x, newValue) else { _x = newValue; return }`, comparing Equatable values with `!=` and plain class references with `!==`), so setting a property to a value equal to the old one stores it but doesn't tell views. `withMutation(keyPath:)` has no such check, so it always notifies. Apple documents none of this. That makes the many hand-written `if x != new { x = new }` guards redundant (harmless), and it matters in two places: arrays of Core Data objects compare by identity, so re-assigning the same students after one was edited sends nothing (B4), and `AppRouter.NavigationDestination` has a custom `==` that ignores its payload (item 22). A small test compiled with this toolchain (`swiftc`, 2026-11-22) confirms it: re-assigning an array of the same `NSObject`s sent 0 notices, an equal `Int` 0, a changed `Int` 1, and a struct whose custom `==` ignores a field stored the new field but sent 0 notices.

## Bugs

### B1. A lesson opened in its own Mac window likely crashes — **checked** in code, not reproduced
`Lessons/Detail/LessonAlbumLinkSection.swift:12` declares `@Environment(AlbumLibrary.self) private var library` (not optional) and reads it in `body` (`:60`). It is drawn for every lesson from `LessonDetailView+InfoSections.swift:29`, and the lesson window (`LessonDetailWindowHost` → `EntityWindowHost` → `LessonDetailView`) is opened by three buttons (`LessonDetailView.swift:118`, `LessonAssignmentHistoryView+Rows.swift:171`, `LinkedNotebookLessonsPanel.swift:93`). The detail-window gate (`AppCore/Windows/DetailWindowScene.swift:166-172`) puts in the classroom, calendar, router, save and restore coordinators, and neither it nor `EntityWindowHost` puts in `AlbumLibrary`; only the main window (`CosmicDaybookApp+MainWindow.swift:67`) and the album window (`CosmicDaybookApp.swift:173`) do. A missing non-optional environment object is a fatal error. The section has been there since at least 2026-09-17 and no bug hunt mentions a crash, so whoever fixes it starts by reproducing it. **Fix:** `.environment(AlbumLibrary.shared)` in the gate, beside the restore coordinator. The same gap is in `AppCore/PreviewEnvironment.swift:23-35` (no `AlbumLibrary`, no `RestoreCoordinator`), so previews of those screens would crash too. S, safe.

### B2. Ready and Brewing can stay stale after two updates overlap — **checked**
`Presentations/Overview/PresentationsViewModel.swift:207-230` saves the "what I last saw" hashes and `lastUpdateDate`, then yields at `:258-259` and returns if cancelled, before it sets `readyLessons`/`blockedLessons`/`blockingResults` at `:273-275`. A second `update()` (the 200 ms debounce, the appear task, memory pressure) cancels the first during that yield, sees nothing changed (`:201`), and returns. The lists keep their old values, or stay empty on first load, until some input changes again. **Fix:** move the hash and date writes below the last cancellation check. S; only the cancelled path changes.

### B3. Every Notes tab leaks its view model — **checked**
`Students/Notes/StudentNotesTimelineView.swift:12-21` stores a reload closure on the model as an Objective-C associated object, and `:45-47` sets it to `{ newViewModel.fetchAllNotes() }`. The closure holds the model and the model holds the closure, so the model, its student and its note rows are never freed. It also needs a `nonisolated(unsafe)` key. **Fix:** delete the extension, the setup and `reload()` (`:502`); call `viewModel.fetchAllNotes()` at `:106` and `:122`. S, safe: that closure was the only thing `reload()` ever did.

### B4. The roster doesn't tell views when a student is edited — **checked** (the mechanism is tested; which screens show it isn't)
`Students/Roster/RosterStore.swift:55-67` rebuilds `all`, `enrolled` and `byID` from the fetched results controller. After a rename or level change they hold the same objects in the same order, so with the equal-value skip none of the three notifies, which contradicts the class comment ("invalidated through observation when the controller reports a change"). Views that show `student.fullName` or group by `student.level` from `roster.all` without observing the row object could stay stale until something else redraws them. `shortNamesByFullName` still notifies on a rename (it holds strings). **Fix:** wrap the three assignments in `withMutation(keyPath:)`, which has no equality check, so they always notify, as designed. Needs care: those views redraw a little more, which is the original intent. Confirm with a test that renames a student and watches `roster.all`.

### B5. Two screens change tracked state while they draw — **checked** (Progress), reported (Checklist)
- `Students/Progress/StudentProgressTabViewModel.swift:32`: `lessonsByID` is tracked, and `lesson(for:)` (`:79-89`) fills it from `reportTitle(for:)`, which the view calls while drawing (`StudentProgressTab.swift:323`). Each miss invalidates the view mid-draw. **Fix:** `@ObservationIgnored` on `lessonsByID`, `context`, `studentID`, `allWorkModels`. S, safe.
- `Lessons/Checklist/ViewModels/ClassSubjectChecklistViewModel.swift:134,252-265`: `cachedLessonsBySequence` is tracked and filled by `lessonsSequenced(sequence:)` inside the grid's `ForEach`. Don't just ignore it: its reset is what forces a redraw after a filter or remote change. **Fix:** an ignored cache plus a tracked generation counter read on each lookup (or build the cache in `applyFilters()`). M, needs care; check with `Self._printChanges()`.

### B6. "Last backup" on the Backups card doesn't update on its own — reported
`Settings/SettingsViewModel.swift:62-69` reads and writes UserDefaults through a computed property, which Observation can't see. The card shows a new date today only because another tracked value changes at the same moment. An automatic backup while the card is open doesn't show. **Fix:** `access(keyPath:)` in the getter, `withMutation(keyPath:)` in the setter. `SettingsDashboardViewModel.swift:44,48` builds a whole `SettingsViewModel` just for this, and the key is spelled again in `Backup/BackupVerification.swift:46`; a small `LastBackupStamp` helper removes both. S, safe.

### B7. Two quick follow-ups in the planning assistant can lose one — reported
`Planning/AIPlanning/LessonPlanning/LessonPlanningViewModel.swift:102-137` has no in-flight guard, and the "Why?" button stays enabled while a reply loads (only the text field is disabled). Each call copies the session; whichever finishes last overwrites the other's question and answer, and the first to finish clears the spinner early. **Fix:** `guard !isLoading` at the top. S; a "Why?" tap during a reply is ignored, as the text field already is.

## Improvements that need care (same results, different timing or redraws)

These follow Apple's guidance but move when something happens, so each wants a check in the app.

11. **Expensive work in `@State` defaults.** Apple's `State` page (updated 2026-10-08): a state property "always instantiates its default value when SwiftUI instantiates the view… avoid side effects and performance-intensive work when initializing the default value", and defer object creation to `task`. `PresentationGroupNoteSection.swift:14` and `CommandBarSheet.swift:40` build a `CommandBarViewModel`, which builds an `SFSpeechRecognizer` (`SpeechRecognitionService.swift:53`); the group-note one rebuilds on every keystroke in the parent. `QuickNoteSheet.swift:60/68` builds an `NLTagger` per redraw. `AlbumIntelligence.init()` starts an availability probe, and `AlbumsRootView` probes again in `.task`. **Fix:** make the recognizer and tagger `lazy` (one change covers every owner), and drop the probe from `init`. S.
12. **The meeting screen redraws whole on every keystroke.** `MeetingSessionView.swift:274-275,288` reads `draft.isEmpty`, which builds the whole `CurrentMeetingData` and so subscribes the parent to every field; it's read twice. Pass `draft` to the footer and menu and read it there, as `CompactDecisionPager` already does. M.
13. **The Ready section runs a fetch and a school-calendar walk in `body`.** `PresentationsViewModel+Filtering.swift:238-280` (`overdueReady`, `recentlyMissed`, an attendance fetch) runs on every chip tap. Compute both in `updateAsync` and add attendance and the day to the change hash, so "Missed" refreshes on attendance changes rather than on whatever redraw comes next. M.
14. **Whole-table fetches for one screen.** Work page peers (`WorkDetailViewModel+Peers.swift:24`, every work row), Notes tab (`StudentNotesViewModel.swift:171-172, 279-280`, every note-on-presentation and every lesson, plus a force-unwrap), meeting draft (`MeetingDraftModel+Fields.swift:96-103`, the whole lesson table per child; `lessonCatalog.all` exists), developmental traits (every `CDNote`, filtered by date in memory). Each becomes a predicate. M.
15. **Year plan pace counts in `body`** (`StudentYearPlanViewModel.swift:227-288`) recompute on every popover; the file's own rule says count at load. M.
16. **Three-Year View rebuilds twice on load** (`StudentCurriculumMapView.swift:40-45`, same in `ClassGridYearsView.swift:69-74`): the `.task` rebuilds, then `onChange(of: loadedAt)` rebuilds again. S.
17. **Unstructured tasks that outlive their screen.** `LessonPlanningViewModel` (`:83-98`, `:113-136`) keeps the model and the model call running after the assistant closes; store and cancel, or make it `async` and call from `.task`. `SettingsViewModel.calculateEstimatedBackupSize` (`:93-98`) is synchronous work in a `Task` restarted on every `onAppear`; call it from `.task`. S–M.
18. **Teardown.** `PresentationsViewModel.swift:71-79` uses `nonisolated(unsafe)` so its `deinit` can remove observers; Swift 6.2's `isolated deinit` (SE-0371) does it without the escape hatch; the model lives for the whole app, so this is hygiene. Try it with a compile first: how `deinit` behaves under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is still open (a Swift Forums thread calls the current behavior a bug, last reported unfixed on Xcode 27 in October 2026). `SchoolYearStore.swift:121-130` never cancels its sync loop. Keep the existing NotificationCenter observers in Presentations: they deliberately filter saves on the posting thread, and Core Data's typed `DidSaveMessage` and `ObjectsDidChangeMessage` are main-actor messages (`CoreData.swiftinterface:1152,1170`), so they can't do that. S.
19. **Newer Observation and notification APIs.** `Backup/RestoreCoordinator.swift:15-36` re-arms `withObservationTracking` by hand; `Observations { … }` (iOS/macOS 26, `Observation.swiftinterface:142`; the element must be `Sendable`, and a pair of Bools is) is the async-sequence form. `MCPIdleQuitController.swift:27-34,69-76` can use the typed macOS 27 messages (`addObserver(of: NSWindow.self, for: .didMiniaturize)` and likewise `.didChangeOcclusionState`, `.willClose`, `.didBecomeKey`, `.didDeminiaturize`, and `NSApplication`'s `.didUnhide`, all main-actor, `AppKit.swiftinterface:4071-4121`) as `IdleMemoryTrimController` does, keeping its `Task` hop and still calling `removeObserver(_:)` on the tokens: Apple's page says observation ends when the token goes out of scope, but the SDK's token is a plain struct with no visible teardown. S.
20. **One source of truth.** The attendance band keeps the sort key twice (`AttendanceExpandedView.swift:35,62,215,276`); the Class Grid checklist mirrors lens, area, child filter and search between `viewModel` and `ClassGridScope` both ways through `onChange` (`ClassGridChecklistView.swift:90-168`). S and M–L.
21. **Stable identity.** `DevelopmentalTraitCardData.id = UUID()` (`DevelopmentalTraitsViewModel.swift:110-111`) and meeting note rows (`StudentNotesViewModel.swift:258`) get new ids on every load, so every row is torn down and rebuilt. Use the characteristic and the meeting id. S.
22. **`AppRouter.NavigationDestination`'s custom `==`** (`AppRouter.swift:53-55`) compares only the case name, so with the equal-value skip a second `.newLesson(area:)` with a different area is stored but doesn't notify (the test above shows exactly this). 23. **Checklist cursor and selection** redraw every visible row on each arrow key and drag step (`ClassGridChecklistView+Grid.swift:222-240`). The hover split in `ChecklistHover.swift` is the precedent. Measure in Instruments before doing it. L.
