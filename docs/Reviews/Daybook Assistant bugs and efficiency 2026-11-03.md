"Confirmed" means the code path was traced end to end. "Plausible" means the path is real but the trigger depends on timing, data, or something Apple doesn't document. "Bug" means the app does the wrong thing and the fix restores what was meant; "waste" means the app does the right thing more often or more expensively than it needs to, and the fix is invisible.

## What runs through all of it

- **Computed properties that fetch.** The Classroom sheet, the setup pages, the front-desk screen and the grid each read the same settings, membership or send rows several times per redraw because the reads sit behind `var` getters (#8, #18, #20, #26, #27).
- **Per-tile work that is per-day.** The grid works out the day's phase, the menu list and who she is once for each of 22 tiles (#3), and Restock rebuilds its fixed colors per tile (#22).
- **A stop that doesn't stop the run.** The ParentLocker sync's `stop()` and the share attacher's watchdog both let go of a task that keeps running and then writes stale state (#1, #10).
- **Two readers of one event.** A return to the app, a first open of a tab, a Siri change: each reaches the same load from two or three triggers (#6, #23, #24).

## Sync, joining and ParentLocker's record

1. **A ParentLocker send under way when the stack is rebuilt is never recorded, so every phone's "attendance is late" reminders keep ringing.** Plausible, medium. Bug. `Daybook Assistant/Sync/AssistantStack.swift:100-108`, `AssistantBootstrapper+ParentLocker.swift:15-23`, `Cosmic Daybook/Attendance/ParentLocker/ParentLockerSync.swift:285-293`, `ParentLockerSync+Schedule.swift:75-77, 250-259, 293-313`, `ParentLockerSync+Run.swift:340-344`. A rebuild removes the stores and calls `stop()`, which cancels the wake task but not `activeRun`; the network save goes through, `recordSend` fails on the dead context, and the stopped sync's `saveOwed` writes its stale view over the new sync's. The new sync's `loadOwed` brings the whole-class send back as attempt 1, which compares against an empty "last seen" and finds every marked child "changed elsewhere", so nothing is saved and `recordsSend` returns false; the guide's backstop ends the same way. ParentLocker has the class, every line says "Not sent", and the 8:50 and 9:00 reminders ring until someone taps Send Now. *Fix:* the rebuild waits for `parentLocker?.activeRun` as it already waits for the share attacher, and a stopped sync writes neither `unsent` nor records. *Test:* none; a `ParentLockerSync` test with a hanging transport, then `stop()`.
2. **A successful import lifts the filing hold even on a container that can't share, so waiting marks are sent into it.** Plausible, medium-low. Bug. `Daybook Assistant/Sync/AssistantFilingHold.swift:81-87, 108-117`, `AssistantStack.swift:63`, `AssistantBootstrapper+AccountDecision.swift:76-86`. The hold's own comment says an import can work once the account arrives "while sharing never does on that container", which is why `setupFailedForAccount` and `mirroringDied` are never cleared; but `stopReason` and `wait` read only `heldSince`, so the first successful import empties it and `onLift` runs `retryWaiting()`. The attacher then calls `share(_:to:)` on the account-less or dead-delegate container before the bootstrapper's account check rebuilds the stack, which on a joined phone runs only on a foreground return or an account change. *Fix:* `stopReason` and `wait` stay non-nil while `setupFailedForAccount || mirroringDied`, and `onLift` isn't called then; a rebuilt stack gets a fresh hold. *Test:* three lines in `AssistantFilingHoldTests`.
3. **Every grid redraw redoes the same day-level work 22 times, and a change to one child redraws all 22 tiles.** Confirmed, medium. Waste. `Daybook Assistant/Attendance/AssistantAttendanceView.swift:397-443`, `AssistantAttendanceViewModel.swift:205-224`, `Cosmic Daybook/Sharing/ClassroomIdentity.swift:23-24, 140-143`, `Cosmic Daybook/Attendance/Tile/AttendanceTile+Menu.swift:13-62`. Per tile, `tile(...)` re-reads `menuStatuses`, `isFuture` (twice), `statusAfterTap(for:)` and `allowsPickup(for:)`, about 15 `Calendar.current.startOfDay` calls, and `markerName` does two UserDefaults reads and trims per tile. Every tile takes closures, so SwiftUI can't skip any; a tap or any import re-runs all 22 bodies, each rebuilding its menu header and VoiceOver label through the date formatter. The 10-07 check's open item #13 was one slice of this. *Fix:* in `grid`, work out `menuStatuses`, `isFuture`, the hint strings and the two identity reads once per body and pass them in; optionally an `Equatable` wrapper around the tile comparing `row`, `tapTarget`, `canMark`, `height`, `markedBy`, `menuStatuses`, the ripple values and whether `onPickup`/`onBack` exist. *Test:* none practical; a hoisted helper could be.
