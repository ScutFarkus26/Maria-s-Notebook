# Build settings and why

Moved verbatim from `Cosmic Daybook/CLAUDE.md` on 2026-10-02 so that file keeps only the rules every session needs. Dates in the notes are when each change landed.

**Build-setting rules** (see `Documentation/Implementation/BUILD_AND_LAUNCH_PERFORMANCE_PLAN.md`):
- The scheme's `-InitializeCloudKitSchema` launch argument stays **unchecked**. Tick it for one run after a Core Data model change, verify in CloudKit Console, then untick it — every Debug launch with it on pays a synchronous CloudKit round-trip inside `CoreDataStack.init`. Apple allows schema setup only in Development, so a Production build ignores the argument: build the schema run with `CLOUDKIT_ENVIRONMENT=Development` (in a simulator, not on the guide's Mac — a Development build of a newer schema would migrate the Mac's Development notebook forward, and an older build then refuses to open it).
- **`CLOUDKIT_ENVIRONMENT`** (project-level; `Production` since the notebook moved there on 2026-09-28, with Development kept frozen on each device as the fallback) sets the `com.apple.developer.icloud-container-environment` entitlement in both apps and the `CloudKitEnvironment` Info.plist key. Change it only in the project, never in one target or one file; see CloudKit Notes → Environments.
- Explicit modules (`SWIFT_ENABLE_EXPLICIT_MODULES`), incremental Debug compilation, and DWARF-only Debug info (`DEBUG_INFORMATION_FORMAT = dwarf`) are deliberate; do not override them per target or switch Debug to whole-module. Explicit modules are also what compilation caching requires.
- **Compilation caching** is on for Debug (`COMPILATION_CACHE_ENABLE_CACHING = YES`, capped by `COMPILATION_CACHE_LIMIT_SIZE = 10G`; the store is `~/Library/Developer/Xcode/DerivedData/CompilationCache.noindex`, shared by every DerivedData folder). It replays a job only when its inputs are identical, and a Swift batch job's inputs are the *whole* module, so after any edit to any app file every compile job misses (2026-09-23: an identical tree at another path replayed 324/324 jobs, Swift compile 1,871 s → 34 s; after a one-line edit, 0 of 55). It pays off on Clean Build Folder, a deleted DerivedData, returning to an already-built tree, and a new worktree's first build — not in the edit loop. Project prefix mapping stays off in the project so Xcode's debug info keeps real source paths; the worktree recipe turns it on for command-line builds (their objects record `/^src/…`, which each target's `compilation-prefix-map.json` maps back), so worktree builds share entries with each other but not with Xcode's own builds.
- **Agent worktrees: build before you edit.** A fresh worktree of an already-built commit replays its whole first build from the cache; once anything is edited, nothing replays and that first build is a full cold compile. So run the worktree recipe once right after creating the worktree, then edit — later builds are incremental in that worktree's DerivedData. When fanning out several agents, build the first worktree before launching them; the build lock queues the others behind it and each then replays.
- Debug compiles in ~20 batch jobs, not 55: `-driver-batch-size-limit 70` in the project's Debug `OTHER_SWIFT_FLAGS`. Each batch job re-checks the declarations it references from other files, so fewer, larger jobs cut compile CPU by 9% (2026-09-23). Clean-build wall clock on an idle Mac barely moves (the single emit-module job is the long pole); it helps when the Mac is hot or busy. Use the size limit, not `-driver-batch-count`, which would split a three-file incremental build into many jobs.
- **Every edit pays ~16 s of emit-module.** Even a one-line change inside a view body re-runs the module's emit-module job, which re-checks all ~107k declarations and ~9.6k macro expansions of the module (2026-09-23: a 26 s edit-build was 16 s emit-module, 4 s planning, 0.7 s compiling the file). Function bodies are 0.4 s of it, so no code-style change shrinks it; only a smaller module would (see the plan's Phase 6).
- **Extensions live in their own files.** An extension has no dependency fingerprint, so any signature-level edit anywhere in a file that contains one — even a new `private func` unrelated to it, and even when the extension itself is `private` — recompiles every file that uses the extended type (2026-09-23, same one-line edit: 3 files in a plain file; 451 beside `extension CDStudent`; 1,069 in `StudentEntity+Roster.swift`; 1,109 beside `extension View`; 1,267 of 1,352 beside a `private extension String`). Edits inside a function body do not trigger it. So keep extensions — together with the `private` modifier they wrap, if any — in `<Type>+<Topic>.swift` files that rarely change, never at the bottom of a view, view-model, store, or service file; a ViewModifier may share a file with its one-line `extension View` wrapper. On 2026-09-23 the extensions in thirteen such files moved into twelve new ones (`StepProtocol.swift`, `LessonPresentationEntity+FollowUp.swift`, `Utils/Extensions/Identifiable+Retroactive.swift`, `Utils/Extensions/Color+Hex.swift`, `ToastOverlayModifier.swift`, …); `Backup/SaveCoordinator.swift` and `Students/Models/StudentModel.swift` still mix because the Daybook Assistant compiles them by path.
- **Prototype new entity members locally, then promote once.** Adding one computed property to `CDStudent` recompiled ~500 files. While a helper is still changing, write it as a `private func` in the file that uses it (3 files recompiled per edit); move it onto the entity once it has settled, in one build.
- There are no script build phases. If one is ever added (SwiftLint, codegen), it must declare input and output file lists, or Xcode re-runs it on every build and invalidates downstream products.
- Debug builds warn on functions and expressions that take over 400 ms to type-check (raised from 100 on 2026-09-21). The numbers are per batch job and wall-clock: each batch job (~20 since 2026-09-23; 47 when this was measured) lazily type-checks the declarations it references from other files (`@State`/`@FetchRequest` macro expansions, memberwise inits) and charges them to whichever body touched them first, so at 100 ms a plain `SomeView(student:)` call or a five-case `switch` was flagged — 60-odd false positives that hid real warnings. Batch-job noise peaks around 320 ms, so anything over 400 is a genuinely pathological expression: confirm it with `python3 Scripts/typecheck_timing.py <build.log>` (one whole-module job, every declaration checked once; 2026-09-21: no body over 100 ms, 12 s of body checking total). That number is wall-clock and tracks the machine's thermal state: after hours of builds the same commit read 20 s and 4 bodies over 100 ms, and three back-to-back runs went 21 → 17 → 13 s as the Mac cooled — so compare two commits only A/B/A on the same machine, never a fresh reading against a stored one. Then give it Apple's treatment — an explicit type on a complex initial value, or a nested ternary / inferred closure split up.
- Iterate on UI/data with **Run Without Building** (⌃⌘R) when the source has not changed; keep one DerivedData folder per project path.
- A `#Preview` closure is a module-level macro, so the compiler expands and type-checks its body in **every** frontend job for the module (~20 batches in a clean build), not just the file's own. Every preview body therefore lives in a `private struct <File>Preview: View` in the same file and the macro body is the single call `<File>Preview()`. Hoisting all 92 previews cut clean-build type checking by 29% (2026-09-04). `@Previewable @State` becomes `@State private var` on that struct. `python3 Scripts/hoist_previews.py "Cosmic Daybook"` lists any preview that has drifted back; `--apply` rewrites it.
